# Feature Specification: Dify AI 工作流接入

**Feature Branch**: `019-dify-workflow-integration`

**Created**: 2026-10-26

**Status**: Draft

**Input**: 用户希望将判题、解析、采集等 AI 处理从项目内直连模型改为 Dify 工作流编排。Spring Boot 继续负责业务、权限、点数、日志和数据落库，Dify 只负责 AI 编排。第一阶段只改造本地测试环境，生产环境暂不切换。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 本地启动 Dify 环境 (Priority: P1)

本地开发者可以一条命令启动已有 Dify 实例，检查容器、队列和 Web 控制台是否就绪，并在不使用生产密钥的情况下完成本地验证。

**Why this priority**: 没有稳定可复现的本地编排平台，后续业务改造无法独立测试。

**Independent Test**: 在未启动 Docker 的机器上执行本地启动命令，等待就绪后访问本地 Dify 控制台，并能运行状态检查命令看到全部核心服务正常。

**Acceptance Scenarios**:

1. **Given** 本机存在 Dify 安装和 Docker Desktop，**When** 执行本地启动命令，**Then** Docker 引擎、Dify API、Worker、数据库、Redis、Web 和 Sandbox 均可就绪。
2. **Given** Dify 已启动，**When** 执行状态检查，**Then** 能明确报告控制台地址、容器状态、HTTP 状态和队列连接状态。
3. **Given** Redis 口令或容器重建导致队列失效，**When** 执行启动或检查，**Then** 系统明确报错并阻止把环境标记为可用。

---

### User Story 2 - 通过 Dify 完成简答题判分 (Priority: P1)

用户提交简答题后，业务后端仍负责权益检查和扣点，Dify 工作流完成语义判分，后端校验结果并写入练习记录。

**Why this priority**: 判题是目前最核心、最容易因模型或提示词变化产生业务口径漂移的 AI 能力。

**Independent Test**: 使用可控的 Dify 测试响应提交一份简答题答案，确认返回结构不变、点数正确扣除、业务记录和调用日志均写入。

**Acceptance Scenarios**:

1. **Given** 用户点数充足且 Dify 判题工作流可用，**When** 用户提交简答题，**Then** 返回原有的 `verdict`、`score`、`feedback` 和参考答案结构。
2. **Given** Dify 判题失败、超时或返回无效结构，**When** 用户提交答案，**Then** 本次点数全额退回且失败原因被记录。
3. **Given** Dify 请求正在进行，**When** 后端等待工作流结果，**Then** 不持有数据库事务或点数账户行锁。

---

### User Story 3 - 通过 Dify 完成解析与题库提取 (Priority: P2)

用户请求 AI 解析、文本导入或截图导入时，Dify 对应工作流生成解析结果或题目 JSON，后端继续负责结果校验、去重、落库和异步保存。

**Why this priority**: 解析和采集调用频率高，迁移后可统一在 Dify 侧维护提示词、模型路由和工作流版本。

**Independent Test**: 分别调用解析、文本出题、截图出题三条路径，确认前端响应契约不变、题目结构合法、解析仍能异步写入解析库。

**Acceptance Scenarios**:

1. **Given** 用户再次点击 AI 解析，**When** Dify 工作流成功返回 Markdown，**Then** 解析结果立即返回并按现有队列异步覆盖解析库。
2. **Given** 文本导入被分成多个片段，**When** 每个片段调用 Dify 文本出题工作流，**Then** 返回的题目遵循现有题目 JSON 结构并继续执行去重与权限校验。
3. **Given** 用户上传不超过 5MB 的截图，**When** 调用 Dify 截图工作流，**Then** 图片经 Dify 文件接口传递并返回可导入的题目列表。
4. **Given** 网页因 robots.txt 不允许抓取，**When** 用户尝试网页导入，**Then** 后端仍直接拒绝，不把该 URL 或抓取任务交给 Dify。

---

### User Story 4 - 观察、隔离和回退 AI 调用 (Priority: P3)

管理员和开发者可以区分每次 AI 调用对应的 Dify 工作流、运行记录、耗时、Token 与结果状态，并确保工作流密钥不进入仓库或浏览器。

**Why this priority**: 外置编排平台增加了一处故障边界，必须可追踪、可隔离且可确认没有隐式直连模型。

**Independent Test**: 触发成功、工作流失败、网络超时和无效输出四类调用，检查日志记录、点数账本、错误响应与密钥暴露情况。

**Acceptance Scenarios**:

1. **Given** Dify 调用成功并返回运行信息，**When** 请求结束，**Then** AI 调用日志包含用途、工作流标识、外部运行标识、耗时、Token 和成功状态。
2. **Given** 本地测试环境启用 Dify，**When** 执行判题、解析或提取，**Then** 项目不会直接请求模型供应商接口。
3. **Given** 工作流密钥缺失或无效，**When** 用户触发 AI 功能，**Then** 返回可理解的“AI 编排服务不可用”，不泄露密钥或供应商错误详情。

### Edge Cases

- Dify 容器未启动、启动中或 HTTP 返回 502 时，功能必须失败并退款，不得无限等待。
- Dify 返回空输出、非 JSON、缺少必填字段或题目数组为空时，视为工作流失败。
- Dify 未返回 Token 用量时，日志应记录零值，不能阻断业务响应。
- Dify 返回的题目类型、难度或选项结构非法时，由后端归一化或拒绝。
- 工作流调用超时后，不允许后端自动重放，避免用户重复扣点和重复生成。
- 截图超过 5MB、图片格式不正确、Dify 文件上传失败时，应在调用 AI 前或上传阶段给出明确错误。
- 同一用户短时间重复点击时，仍受现有新账号额度、接口限流和点数余额限制。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 本地测试环境 MUST 能启动、停止和检查现有 Dify 实例，并明确报告不可用原因。
- **FR-002**: 本地 Dify MUST 与项目本机 MySQL、Redis 和支付侧车使用独立容器或独立端口，避免共享数据。
- **FR-003**: 系统 MUST 提供四个独立 AI 工作流：简答题判分、题目解析、文本出题、截图出题。
- **FR-004**: 工作流定义 MUST 版本化保存在仓库中，可通过导入方式重建，不依赖仅存在于 Dify 数据库中的手工配置。
- **FR-005**: Spring Boot MUST 继续作为业务与数据唯一来源，负责鉴权、题库归属、权限、点数、退款、限流、结果校验和落库。
- **FR-006**: Dify MUST 只接收完成 AI 编排所需的最小输入，并只返回当前业务所需的输出。
- **FR-007**: 前端和移动端 MUST NOT 直接访问 Dify，也 MUST NOT 获取任何工作流密钥。
- **FR-008**: 本地测试环境中的判题、解析、文本出题和截图出题 MUST 通过 Dify 调用，不直接调用模型供应商接口。
- **FR-009**: 现有用户 API 的请求和响应契约 MUST 保持不变，前端无需因本次架构切换而改接口。
- **FR-010**: 点数 MUST 在调用 Dify 前按现有规则扣除；工作流失败、超时、输出无效或服务不可用时 MUST 全额退回。
- **FR-011**: AI 调用期间 MUST NOT 持有数据库事务或点数账户行锁。
- **FR-012**: 每次 Dify 调用 MUST 写入 `ai_call_log`，记录用途、工作流或模型标识、外部运行标识、Token、耗时和成败。
- **FR-013**: Dify 返回的结果 MUST 经过后端结构校验和归一化后才能进入练习记录、解析库或题库。
- **FR-014**: 网页采集 MUST 继续由后端执行 robots.txt 合规检查；只有允许抓取的网页文本可送入 Dify。
- **FR-015**: Dify 文件上传 MUST 支持现有截图格式和 5MB 限制，且上传临时文件不得进入仓库。
- **FR-016**: Dify 工作流密钥、模型供应商密钥和外部运行数据 MUST NOT 写入源码、测试夹具、日志或前端资源。
- **FR-017**: 本地自动化测试 MUST 使用可控的 HTTP 测试服务模拟 Dify，不依赖真实模型、真实 Token 或公网。
- **FR-018**: 本地测试环境 MUST 提供真实 Dify 冒烟验证，覆盖健康检查及四个工作流调用。
- **FR-019**: 本阶段 MUST NOT 切换或部署生产环境的 AI 调用路径。
- **FR-020**: 工作流提示词 MUST 继承现有业务约束，包括默认 Java 风格伪代码、禁止提到考生选项对错、解析结果可直接存入解析库。

### Key Entities

- **AI 工作流**：一个可版本化的 Dify 编排定义，包含用途、输入变量、输出结构、提示词和模型配置。
- **AI 调用记录**：一次业务 AI 请求的后端审计记录，关联用户、用途、工作流、外部运行标识、Token、耗时和结果状态。
- **点数流水**：AI 调用的扣费与失败退款记录，是用户权益和成本的唯一账本。
- **导入任务**：文本或截图出题的异步业务任务，保存来源、进度、提取结果和错误。
- **题目解析库**：题目当前的 AI 解析内容，由后端接收工作流结果后异步更新。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本地开发者可在 5 分钟内从 Docker 停止状态启动 Dify，并通过单一状态检查确认所有核心服务可用。
- **SC-002**: 判题、解析、文本出题、截图出题四条路径在本地烟雾测试中全部成功，且返回结构与现有调用方兼容。
- **SC-003**: 成功、失败、超时和无效输出四类 AI 调用的点数账本结果 100% 正确，无重复扣费或漏退款。
- **SC-004**: 所有本地测试路径中直接模型供应商调用次数为 0，Dify 工作流调用次数与成功业务调用次数一致。
- **SC-005**: 密钥扫描结果为 0 个真实密钥或工作流 Token 进入仓库。
- **SC-006**: 后端全量测试和前端生产构建均通过，现有用户流程无需前端改动即可完成本地验证。

## Assumptions

- 第一阶段只改造本地和测试 profile，生产继续使用当前直连模型实现。
- 本地 Dify 使用现有 `D:\dify` 安装和 Docker Desktop，不重新复制一套源码。
- Dify 自己管理模型供应商密钥，项目只保存各工作流的服务 API Token。
- 文本切块、文档文本提取、robots.txt 校验、题库去重和数据库写入仍属于业务后端职责。
- 真实 HTTP 冒烟测试需要的 Dify 工作流 Token 只写入本机 `.env.local` 或进程环境变量。
