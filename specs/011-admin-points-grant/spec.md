# Feature Specification: 管理员后台赠送点数

**Feature Branch**: `011-admin-points-grant`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "管理员账号可以在后台管理对指定账号赠送点数"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员按账号邮箱赠送点数 (Priority: P1)

管理员在后台输入目标账号邮箱，确认账号身份和当前点数后，填写赠送点数与原因并提交。系统完成加点和流水记录，管理员与目标用户都能看到最新余额。

**Why this priority**: 这是客服补偿、活动奖励和问题处理的核心运营能力。

**Independent Test**: 使用管理员账号向一个普通账号赠送点数，确认目标账号余额增加、点流水新增、操作人和原因可追溯。

**Acceptance Scenarios**:

1. **Given** 管理员进入后台赠点页面，**When** 输入存在的账号邮箱并查询，**Then** 系统展示该账号昵称、邮箱、账号状态、当前可用点数和最近流水。
2. **Given** 管理员已确认目标账号，**When** 填写正整数点数和赠送原因后提交，**Then** 目标账号点数立即增加，并显示赠送成功。
3. **Given** 管理员完成赠送，**When** 查看目标账号的点数流水，**Then** 流水包含赠送点数、操作原因、操作管理员和操作时间。
4. **Given** 目标用户重新进入点数页面，**When** 页面刷新，**Then** 用户看到增加后的可用余额和对应赠送流水。

---

### User Story 2 - 权限与输入安全校验 (Priority: P1)

普通用户和被冒用的请求不能执行账号查询或赠送操作；管理员输入不存在账号、非正整数、缺失原因或超大点数时，系统拒绝并给出明确提示。

**Why this priority**: 赠点直接改变付费资产，任何越权或重复提交都会造成资金和账本风险。

**Independent Test**: 分别以普通用户、其他用户伪造请求和管理员非法输入调用接口，确认均被拒绝且余额不变。

**Acceptance Scenarios**:

1. **Given** 未登录用户或普通用户，**When** 请求查询目标账号或赠送点数，**Then** 系统返回拒绝访问。
2. **Given** 管理员，**When** 查询不存在的邮箱，**Then** 系统提示账号不存在。
3. **Given** 管理员，**When** 输入 0、负数、小数、超过 100 万的点数或空原因，**Then** 系统拒绝且余额不变。
4. **Given** 管理员在短时间内用相同幂等键重复提交，**When** 请求被重复发送，**Then** 只到账一次，第二次返回第一次的成功结果。

---

### User Story 3 - 管理端可审计与可辨认 (Priority: P2)

管理员在后台可以清楚看到赠送目标、当前余额、赠送后的预计余额、操作原因以及最近操作结果，避免误送给错误账号。

**Why this priority**: 仅靠邮箱容易选错账号，明确展示账号状态和余额能降低运营误操作。

**Independent Test**: 管理员查询两个不同账号，确认当前账号信息随查询结果刷新，成功赠点后余额与流水同步更新。

**Acceptance Scenarios**:

1. **Given** 管理员修改查询邮箱，**When** 查询成功，**Then** 页面清除上一个账号的信息并展示新账号。
2. **Given** 赠点成功，**When** 结果返回，**Then** 页面更新目标用户当前余额，并允许管理员继续赠送。
3. **Given** 赠点失败，**When** 页面显示错误，**Then** 目标账号和余额不应显示为已成功更新。

### Edge Cases

- 邮箱查询忽略首尾空格和大小写差异。
- 目标账号不存在时只返回通用“账号不存在”，不泄露其他账号数据。
- 赠送原因去除首尾空格后不能为空，且限制在 2 至 100 个字符。
- 单次赠送点数必须为 1 至 1,000,000 的整数；账号总余额不设上限。
- 同一管理员重复使用相同幂等键时只能成功赠送一次。
- 不同管理员分别提交相同点数和原因时属于两次独立赠送。
- 赠送事务失败时，余额、流水和幂等记录必须全部回滚。
- 账号删除或不可用时，不执行赠点。
- 管理端查询和赠送接口均需限流，防止脚本批量枚举邮箱。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 仅允许管理员查询赠点目标账号和执行赠点。
- **FR-002**: 管理员 MUST 能按完整邮箱查询目标账号。
- **FR-003**: 查询结果 MUST 展示目标账号昵称、脱敏邮箱、状态、当前可用点数、套餐名称和最近点数流水。
- **FR-004**: 赠点 MUST 要求正整数点数、有效原因和唯一幂等键。
- **FR-005**: 单次赠送点数 MUST 在 1 至 1,000,000 之间，且不能为小数。
- **FR-006**: 赠送原因去除首尾空白后 MUST 为 2 至 100 个字符。
- **FR-007**: 赠点 MUST 在数据库事务内锁定目标账户，原子完成余额增加和点流水写入。
- **FR-008**: 每次成功赠送 MUST 写入一条不可变点数流水，包含目标用户、点数、余额结果、原因、操作管理员、幂等键和时间。
- **FR-009**: 相同管理员使用相同幂等键重复提交时，MUST 返回首次结果且只到账一次。
- **FR-010**: 赠点成功后 MUST 返回目标用户最新可用点数和本次流水信息。
- **FR-011**: 事务失败时 MUST 不产生余额变化或部分流水。
- **FR-012**: 管理员查询和赠点接口 MUST 设置应用层限流。
- **FR-013**: 普通用户、未登录用户和伪造管理员请求 MUST 无法调用查询或赠点接口。
- **FR-014**: 后台页面 MUST 提供邮箱查询、账号摘要、点数输入、原因输入、提交状态、成功提示和错误提示。
- **FR-015**: 页面 MUST 在查询新账号或成功赠点后刷新目标账号余额与近期流水。
- **FR-016**: 点数页面提供给用户的流水 MUST 显示管理员赠送类型及原因，不暴露管理员敏感信息。

### Key Entities

- **管理员赠点请求**：记录目标账号、点数、原因、幂等键、操作管理员、执行结果和时间。
- **点数账户**：目标账号当前赠送余额与可用点数，是赠点的加锁更新对象。
- **点数流水**：余额变化的不可变审计记录，供管理员和用户查询。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员能在 1 分钟内完成账号查询并提交一次赠点。
- **SC-002**: 100% 的成功赠点都能在目标用户点流水中追溯到点数、原因、操作管理员和时间。
- **SC-003**: 相同幂等键重复提交 10 次时，只产生 1 次余额增加和 1 条赠送流水。
- **SC-004**: 普通用户越权请求的成功率为 0。
- **SC-005**: 非法点数、空原因、不存在账号和事务失败场景下，目标余额变化为 0。
- **SC-006**: 管理员赠点后刷新页面，目标账号余额与后台显示一致。

## Assumptions

- “指定账号”通过完整邮箱识别，首尾空格忽略、大小写不敏感。
- 赠送增加的是可直接消费的赠送点数，不改变付费套餐。
- 管理员可以为自己的账号赠点，但同样必须完整记录流水和原因。
- 页面复用现有管理员后台、点数账户和点数流水模型。
- 不新增邮件或短信通知；目标用户可在点数页面看到余额和流水。
