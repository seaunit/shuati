# 图形验证码安全说明

> 实现位置：`backend/src/main/java/com/shuati/captcha/`
> 适用标准：GB/T 41802-2022《信息技术 验证码程序要求》 + 互联网行业通用安全实践

## 1. 接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/captcha/image` | GET | 返回 `{ ticket, imageBase64, expiresInSeconds }`，**不返回答案** |
| `/captcha/verify` | POST | 入参 `{ ticket, userInputCode }`，成功返回 `{ valid: true }` |

响应沿用项目统一结构：`{ code, message, data }`。

## 2. 逐条对照约束清单

| # | 约束 | 实现情况 |
| --- | --- | --- |
| 1 | 生成/校验全在服务端，一次性，成功即作废 | ✅ 答案只在服务端生成；校验用 Lua 脚本原子执行「命中即 DEL」 |
| 2 | TTL 自动过期（图形 120s） | ✅ `captcha:{ticket}` 写入时带 `EX 120`，Redis 自动过期 |
| 3 | 单 ticket 最多 3~5 次、超过失效；IP/设备限流 | ✅ 默认 5 次，达到上限直接 `DEL`；另有 `captcha:rate:ip:*`、`captcha:rate:device:*` 每分钟限流 |
| 4 | 错误提示统一 | ✅ 所有失败（不存在/过期/输错/超次）统一返回「验证码错误或已过期」 |
| 5 | Redis 存储，key `captcha:{ticket}`，ticket=UUID，禁 HttpSession | ✅ 详见第 3 节；全程不使用 Session |
| 6 | 剔除易混淆字符；噪点/干扰线/旋转扭曲 | ✅ 字符集 `23456789A-HJ-NP-Z`；绘制含噪点、干扰线、干扰圆、贝塞尔曲线、字符随机旋转 |
| 7 | 接口规范 | ✅ 见第 1 节 |
| 8 | 安全红线 | ✅ 不返回答案、不可重复校验、有 TTL、提示不区分、不用 Session |
| 9 | 组件选型 | ✅ 图形验证码基于 EasyCaptcha 1.6.2（`SecureSpecCaptcha` 继承 `SpecCaptcha`）；注意 EasyCaptcha 无旋转，故重写了绘制；高风险场景建议叠加 tianai-captcha 行为验证码 |

## 3. Redis Key 设计

| Key | 类型 | TTL | 说明 |
| --- | --- | --- | --- |
| `captcha:{ticket}` | String(JSON) | 120s | `{"code":"<明文或哈希>","attempts":0}` |
| `captcha:rate:ip:{ip}` | String(计数) | 60s | IP 维度每分钟申请次数 |
| `captcha:rate:device:{deviceId}` | String(计数) | 60s | 设备维度每分钟申请次数 |

ticket 为 32 位 UUID（去横线），不可预测。

## 4. 校验流程（原子）

```
校验请求 → Lua 脚本（单线程原子执行）
  ├─ key 不存在            → EXPIRED
  ├─ attempts+1 后命中      → DEL key，返回 OK（一次性）
  ├─ attempts >= max       → DEL key，返回 LOCKED（作废）
  └─ 其他                  → 回写 attempts（保留原 TTL），返回 MISMATCH
```

三种失败对外都映射成同一句提示，攻击者无法通过提示差异探测 ticket 是否存在或是否过期。

## 5. 存储形态：明文 vs 加盐哈希

- `shuati.captcha.hash-store: true`（默认）：存 `SHA-256(secret + ":" + 大写答案)`；
- `shuati.captcha.hash-store: false`：存明文（仅便于本地调试）。

因为是确定性哈希，比对方式不变。即使 Redis 被读取，也无法直接得到答案。

## 6. 关键配置

```yaml
shuati:
  captcha:
    ttl-seconds: 120            # 有效期
    max-attempts: 5             # 单 ticket 最大尝试次数
    code-length: 4              # 4 或 5
    width: 150
    height: 48
    hash-store: true            # 加盐哈希存储
    secret: ${SHUATI_CAPTCHA_SECRET}
    ip-limit-per-minute: 20     # IP 维度限流
    device-limit-per-minute: 20 # 设备维度限流
```

## 7. 前端接入示例

```ts
// 1. 取验证码
const { ticket, imageBase64 } = await api("/captcha/image");
// imageBase64 直接给 <img :src="imageBase64">

// 2. 提交校验（X-Device-Id 可选，用于设备维度限流）
await api("/captcha/verify", {
  method: "POST",
  headers: { "X-Device-Id": deviceId },
  body: JSON.stringify({ ticket, userInputCode: input.toUpperCase() }),
});
// 失败统一抛「验证码错误或已过期」，前端刷新验证码即可
```

`X-Device-Id` 缺省时后端会用 `User-Agent` 哈希替代，Nginx 会把 `X-Forwarded-For` / `X-Real-IP` 透传给后端做 IP 限流。

## 8. 生产环境注意事项

1. **必走 HTTPS**：验证码图片与 ticket 在明文 HTTP 下可被中间人替换。
2. **Redis 必须设密码并限制来源**，不要暴露到公网；`SHUATI_CAPTCHA_SECRET` 用随机值并单独保管。
3. **阈值按业务调**：登录入口建议 IP 20 次/分、设备 20 次/分；短信验证码另加「同手机号 60s 冷却 + 单日上限」。
4. **图形验证码是低风险方案**：登录、注册、找回密码等高风险入口，建议在图形验证码之外叠加 tianai-captcha 滑块/点选行为验证（校验操作轨迹，而非仅坐标）。
5. **短信验证码**：6 位纯数字，绑定手机号 + 业务场景（如 `sms:login:{phone}`），不可跨场景复用；发送前先过人机验证，防短信轰炸。
6. **监控**：对 `captcha:rate:*` 触发量、`MISMATCH` 次数做告警，可及早发现撞库/打码平台。
7. **不要在前端日志/埋点里打印用户输入与 ticket**。

## 9. 已知取舍

- EasyCaptcha 1.6.2 的 `SpecCaptcha` 只有干扰线与干扰圆、没有字符旋转，因此 `SecureSpecCaptcha` 重写了 `alphas()`（安全字符集）与 `out()`（旋转+噪点），绘制仍复用 EasyCaptcha 的颜色/线条工具方法。
- 本模块是**图形验证码**，不校验行为轨迹；滑块/点选类需求请接入 tianai-captcha。
- 限流为固定窗口实现（`INCR` + `EXPIRE`），足够拦住脚本；如需更平滑可换 Redis 令牌桶。

## 10. 已接入的业务：登录 / 注册

`POST /api/auth/login` 与 `POST /api/auth/register` 已强制要求图形验证码：

| 字段 | 说明 |
| --- | --- |
| `captchaTicket` | `/captcha/image` 返回的 ticket |
| `captchaCode` | 用户输入的验证码字符 |

**校验顺序：先验验证码，再查账号与密码。** 这样未通过验证码的请求根本不会走到账号查询，
既挡住了撞库/批量注册，也无法被用来探测某个邮箱是否存在。

失败语义：

- 验证码缺失、错误、过期、超次 → 统一 400「验证码错误或已过期」；
- 验证码通过后才校验账号 → 密码错误返回 401「邮箱或密码错误」。

前端登录页已接入：进入页面自动拉取验证码；每次提交失败自动换一张（因为验证码是一次性的）。
