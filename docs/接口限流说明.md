# 接口限流说明

> 实现位置：`backend/src/main/java/com/shuati/rate/`
> 存储：Redis（复用验证码模块的 Redis 实例）

## 1. 为什么用 Redis

计数放在 Redis 而不是 JVM 内存，天然支持多实例集群：Nginx 后面的多个后端节点共享同一份计数，
不会出现「每台机器各放 300 次」的漏洞。实现是固定窗口（`INCR` + 首次 `EXPIRE`），
一条命令完成自增，无并发竞争问题。

## 2. 三个层次

| 层次 | 作用范围 | 说明 |
| --- | --- | --- |
| 全局兜底 | 所有 `/api/**`、`/captcha/**` | 同一 IP 每分钟总量上限，拦脚本扫描 |
| 接口级 | 打了 `@RateLimit` 的 Controller 方法 | 按 IP 或用户维度精确限流 |
| 验证码专用 | `/captcha/image` | IP / 设备各 20 次/分钟（见验证码文档） |

## 3. 当前生效的规则

| 接口 | 维度 | 限制 | 目的 |
| --- | --- | --- | --- |
| `POST /api/auth/login` | IP | 10 次 / 分钟 | 撞库 |
| `POST /api/auth/register` | IP | 5 次 / 小时 | 批量注册刷注册赠点 |
| `POST /api/practice/submit-essay` | 用户 | 30 次 / 分钟 | AI 判分成本 |
| `GET /api/practice/questions/{id}/explanation` | 用户 | 60 次 / 分钟 | AI 解析成本 |
| `POST /api/import` | 用户 | 5 次 / 小时 | 文档解析成本 |
| `GET /captcha/image` | IP / 设备 | 20 次 / 分钟 | 验证码接口刷取 |
| 全部业务接口 | IP | 300 次 / 分钟 | 兜底 |

> 未登录时「用户维度」会退化成 IP 维度，避免匿名请求绕过。

## 4. 用法

在 Controller 方法上直接加注解即可：

```java
@PostMapping("/api/practice/submit-essay")
@RateLimit(name = "ai:judge", limit = 30, windowSeconds = 60, scope = RateLimit.Scope.USER)
public ApiResponse<Map<String, Object>> submitEssay(...) { ... }
```

`Scope` 三种取值：

- `IP`：按客户端 IP（会读 `X-Forwarded-For` / `X-Real-IP`，Nginx 已透传）；
- `USER`：按登录用户 ID；
- `IP_AND_USER`：两者都限。

超限统一抛 429，响应体 `{ "code": 429, "message": "请求过于频繁，请稍后再试" }`。

## 5. 配置

```yaml
shuati:
  rate-limit:
    enabled: true        # 总开关
    global-per-minute: 300  # 全局 IP 兜底，0=关闭
```

接口级阈值写在注解里，改完重新部署即可；如需运营期动态调整，可后续把阈值挪到数据库 + 缓存。

## 6. 运维注意

- **fail-open 策略**：Redis 不可用时限流自动放行（打 WARN 日志），避免整站 500。此时验证码校验、AI 相关接口本身也会因 Redis 不可用而失败，所以不会出现「无防护且无感知」。
- **告警**：对 `429` 响应量和 `rate:*` 触发量做监控，可及早发现撞库、打码平台或成本异常。
- **阈值调优**：先按上表跑一段时间，观察真实用户的峰值，再决定松紧。太小会误伤正常用户，太大等于没限。
- **Nginx 层可再加一层**：`limit_req_zone` 可做更前置的连接级限流，与后端限流互补。
- **AI 接口的最终防线是点数**：即使限流被绕过，AI 调用仍会扣点数，账户余额耗尽即无法继续，这是比限流更硬的成本边界。
